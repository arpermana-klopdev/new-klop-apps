## Migration decisions

The permission seed:

- refuses a different server/database or changed role IDs/scopes;
- creates no role, user, platform assignment, tenant permission, or runtime grant;
- maps only existing `SUPER_ADMIN` (RoleId 1) and `PLATFORM_SUPPORT` (RoleId 2);
- refuses duplicate or incompatible permission records and any mapping outside those two roles;
- defaults to no change unless a DBA supplies an approval ticket and explicitly sets `KLOP_APPLY_CHANGES=APPROVED`;
- writes audit records for permission creation and each new role-permission mapping, with actor service, target, ticket, UTC timestamp, result, and correlation ID.

The tenant policy template preserves the deployed SQL parameter/return contracts. It adds active session/user/email verification and tenant membership/status/type checks, tenant permission-scope matching, PERSONAL membership-operation denial, and a tenant-scoped effective-permission result. Role assignment shares the existing `KLOP/TENANT/<TenantId>` application lock, requires one active OWNER, prevents self-assignment and additional OWNER grants, denies `VIEWER` because `IsAssignable=0`, permits only workbook-approved MEMBER/ADMIN targets, and allows ADMIN assignment only by a different active OWNER. Ownership transfer remains on HOLD.

The revised unified-matrix portion keeps the six role records, extends the single `mst.RolePermissions` structure with `TenantTypeId` and `MatrixRowVersion`, and carries each existing tenant grant forward to both active tenant-type contexts. PERSONAL has only OWNER; ORGANIZATION has OWNER/ADMIN/MEMBER/VIEWER. It creates only the two protected matrix access permissions, initially mapped to the existing SUPER_ADMIN role. Account self-service policy rows live in `mst.AccountSelfServicePolicies`; no `ACCOUNT` role scope, account permission-master row, or account grant is created. The original workbook is not in this workspace; account policy values are reconciled from the existing row-level CSV and must be reviewed against the approved source before deployment.

## Least-privilege runtime plan

The prepared allowlist contains exactly **38** procedures:

- 20 existing baseline/authentication/tenant procedures;
- 2 public read-only Terms lookups needed by registration (not legal-document administration);
- 6 registration onboarding procedures;
- 4 read-only platform registration administration procedures;
- 6 permission validation/discovery/matrix procedures, including the tenant resolver, unified matrix read, atomic save/validate, and audit history.

The eight current role grants are a subset of this inventory. The role has no members. The live API runs under an elevated `dbo`/`sysadmin` identity, so its effective permissions are not evidence that the role is configured correctly. A dedicated non-admin Windows/Entra login must be provisioned outside this SQL package; the template never creates a server login or grants direct table access.

The template rejects missing procedures, broad/schema EXECUTE grants, unexpected runtime-role members, nested roles, direct user EXECUTE, table DML/admin permissions, non-approved login types, and non-`dbo` application schema ownership. It does not revoke or overwrite existing privileges. No legal-document admin, approval, role-permission management, or other proposed/HOLD procedure is in the allowlist.

- All scripts guard the expected server/database. The three approval templates also default to `KLOP_APPLY_CHANGES=NO` and an unset ticket. Do not override these without a recorded Development approval.
- `001`, `004`, and `006` are read-only. `002` uses a transaction, `XACT_ABORT`, TRY/CATCH rollback, duplicate/incompatible-row checks, and insert-only idempotency. `003` uses a transaction across `GO` batches and `CREATE OR ALTER`; it has no encompassing TRY/CATCH, so on any error stop immediately and have the DBA inspect/resolve the session transaction before proceeding. `005` is transactional with TRY/CATCH rollback and adds only missing approved objects/membership/grants.
- No script contains `DELETE`, `TRUNCATE`, or `REVOKE`. `003` replaces one unique index to add the tenant-type key and replaces stored-procedure/trigger definitions; preserve current definitions and a verified database backup so an approved rollback can restore prior routines.
