## Safe Development-only Terms bypass proposal

The bypass must **not** mean “accept any draft,” “ignore consent,” “use the bundled PDF,” or “write a permanent approval record.” Recommended behavioral contract, pending approval:

1. A real, immutable Terms version must exist first, with actual content/hash and an explicit PERSONAL and/or ORGANIZATION scope. Current Development has no version rows, so this prerequisite is presently unmet.
2. Add a default-off, Development-only workflow override after security/product/DBA approval. The API must require `IHostEnvironment.IsDevelopment()` and fail startup if override is enabled elsewhere. Configuration must be environment-isolated; SQL must apply the same narrow allow rule to the exact version, not a client flag.
3. The override may treat that exact version as eligible for this Development registration flow despite its document approval/publication state. It must not update the document's approval state or create an approval event.
4. The UI displays the actual document/version and a clear Development-only notice. The acceptance checkbox remains visible, unchecked, and disabled until the document has loaded; the user must explicitly check it and select I Agree.
5. Registration still requires the selected type, exact version ID, and `termsAccepted: true`. The existing transaction persists the real version ID/hash, server acceptance time, source, application, and consent audit. Also record that the Development override was used without changing approval history.
6. Production has no matching flag and rejects any attempt to activate the override. Production document approval/publication and explicit consent enforcement remain unchanged.

Do not introduce a new configuration key, alter `registration.legal_consent_enforcement`, change the current database, or activate the override before those approvals. The current disabled consent-enforcement setting only permits legacy requests without registration intent; it does not make the typed Register request's current Terms version check optional.

## Focused manual test plan — Development only, after explicit approval

**Not executed.** Run only after legal version, runtime identity/grants, provider/sink, test identity, and data-test approvals are documented. Use a local SMTP sink or an explicitly approved non-production recipient; do not send to real users.

1. **Preflight:** Verify the API is running under the approved non-admin Windows identity; verify all 28 procedure grants through the actual runtime identity; confirm Development target and no Production endpoint. Confirm Terms version, immutable hash, scope, and private file are available.
2. **Bypass guard:** With the Development-only switch disabled, verify a draft/unpublished Terms version blocks typed registration. Enable only under the approved Development configuration and verify the exact configured version is eligible. Verify no approval/publication row changes. In a Production-equivalent startup/configuration check, ensure enabling the switch fails closed.
3. **Consent UX:** Open PERSONAL and ORGANIZATION independently. Confirm the document identity and Development notice, unchecked checkbox by default, and disabled submit until the user checks it and selects I Agree. Reload/change type/version and confirm consent resets. Verify the bundled local draft is not silently treated as a database version.
4. **Payload/validation:** Submit valid forms for both types and inspect the request for `fullName`, `email`, `password`, the selected type, exact version ID, and `termsAccepted: true`; confirm no Confirm Password, client timestamp, or hash is sent. Test invalid email, missing name, mismatched confirmation, short password, and length limits.
5. **Atomic registration:** Using only the approved disposable identity, verify one user, one credential, one challenge, one registration application, one append-only consent, and correlated audit records. Confirm consent references the actual version/hash and server time, override use is auditable, and no Tenant/membership/role was created.
6. **Email sender:** Confirm the test sink receives the message; verify sender, HTTPS origin, `/verify-email` route, user ID, token fragment, and expiry text. Do not print or save the token in test output.
7. **Link integration:** Click the verification link and verify the page consumes fragment fields, submits once, clears URL history state, and reports success. Confirm no token is written to storage or telemetry. Retry the consumed token and confirm rejection.
8. **Login gate:** Before verification, attempt login and confirm generic rejection/no session. After verification, confirm the verified account can sign in. Confirm no automatic sign-in from the verification screen.
9. **Resend:** For an unverified disposable identity, resend once and verify generic response, cooldown/rate behavior, new token delivery, and rejection of the old token. Test expired token and abuse limits only through approved controlled test data.
10. **Failure/duplicate:** Simulate sink/provider unavailability in the isolated Development test setup and verify account state remains committed, the failure log contains no token/email/password/secret, and resend recovers. Confirm duplicate submission remains generic HTTP 202 and creates no second active account/application.
11. **Audit and cleanup:** Verify audit/correlation fields and retention expectations. Any cleanup must follow the approved data-change plan; do not reset or directly delete audit/consent records.
